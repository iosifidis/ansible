# 23.3 Branching Strategy 🌿

## Το μοντέλο: 3 branches

Για Ansible projects, το απλό **3-branch model** είναι ιδανικό:

```
main ────────────────────────────────────► production
  │
  └── develop ──────────────────────────► staging (auto-deploy)
        │
        ├── feature/add-nginx-role ──► feature work
        ├── fix/postgres-timeout   ──► bugfix
        └── hotfix/critical-patch  ──► emergency fix (→ main)
```

---

## Τι κάνει κάθε branch

```
main:
  ├── ΠΑΝΤΑ production-ready
  ├── ΠΟΤΕ direct push (protected!)
  ├── Αλλαγές ΜΟΝΟ μέσω PR από develop
  └── Κάθε commit = νέο production deploy (μετά από approval)

develop:
  ├── Ενσωμάτωση feature branches
  ├── Auto-deploy σε STAGING με κάθε push
  ├── Πρέπει να περνά lint + molecule tests
  └── Όταν σταθεροποιηθεί → PR προς main

feature/xxx:
  ├── Δουλειά σε νέο feature ή bugfix
  ├── Βγαίνει από develop
  ├── PR → develop όταν τελειώσει
  └── ΠΟΤΕ απευθείας σε main!

hotfix/xxx:
  ├── Emergency fixes ΜΟΝΟ
  ├── Βγαίνει από main (!)
  ├── PR → main + back-merge σε develop
  └── Χρησιμοποιείται ΣΠΑΝΙΑ
```

---

## GitFlow vs Trunk-Based

```
GitFlow (αυτό που περιγράφουμε):
  main + develop + feature/*

  Πλεονεκτήματα:
  ✅ Ξεκάθαρος διαχωρισμός staging/production
  ✅ Εύκολο για ομάδες
  ✅ Controlled releases

  Ιδανικό για: sysadmins, ops teams, Ansible

Trunk-Based Development:
  ΜΟΝΟ main + short-lived feature branches

  Πλεονεκτήματα:
  ✅ Γρηγορότερο integration
  ✅ Continuous deployment

  Ιδανικό για: dev teams, microservices, high velocity
  Απαιτεί: feature flags, comprehensive tests
```

## Καθημερινή ροή εργασίας

```bash
# 1. Ξεκίνα από develop (πάντα ενημερωμένο)
git checkout develop
git pull origin develop

# 2. Νέο feature branch
git checkout -b feature/add-docker-role

# 3. Δούλεψε στο feature
vim roles/docker/tasks/main.yml
git add -A
git commit -m "feat(docker): add docker installation role"

# 4. Test τοπικά πριν push
ansible-lint
cd roles/docker && molecule test

# 5. Push και άνοιξε PR → develop
git push origin feature/add-docker-role
# → GitHub/GitLab: Create Pull Request → develop

# 6. Μετά τον review → Merge στο develop
# → auto-deploy σε staging!
# → verify στο staging

# 7. Όταν staging είναι ok → PR develop → main
# → approval required
# → deploy σε production!
```

## Commit messages — Convention

```bash
# Ακολούθησε Conventional Commits:
feat(nginx):      add SSL termination
fix(postgres):    increase connection timeout
chore(deps):      update community.docker to 3.8.0
docs(readme):     add deployment guide
refactor(base):   split SSH hardening to separate task
test(nginx):      add molecule test for vhost config

# Γιατί;
# → git log --oneline → ξεκάθαρο ιστορικό
# → Αυτόματο changelog generation
# → Εύκολο grep για συγκεκριμένες αλλαγές
git log --oneline --grep="feat"
```

## Σύνοψη 23.3

```
Branching Strategy
│
├── main     → production (protected, PR only)
├── develop  → staging (auto-deploy on push)
├── feature/ → νέες λειτουργίες (PR → develop)
└── hotfix/  → emergency (PR → main + develop)

Ροή:
feature branch → PR review → develop → staging OK
→ PR review → main → approval → production
```
