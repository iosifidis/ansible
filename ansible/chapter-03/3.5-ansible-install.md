# 3.5 Εγκατάσταση Ansible 📦

## Μέθοδοι Εγκατάστασης

Υπάρχουν **τρεις τρόποι** να εγκαταστήσεις Ansible:

```
┌─────────────────────────────────────────────────┐
│  Μέθοδος 1: apt (OS package manager)            │
│  ✅ Απλό  ❌ Παλιά έκδοση                       │
├─────────────────────────────────────────────────┤
│  Μέθοδος 2: pip (Python package manager)        │
│  ✅ Νέα έκδοση  ✅ Συνιστάται  ⚠️ Virtual env   │
├─────────────────────────────────────────────────┤
│  Μέθοδος 3: pipx                                │
│  ✅ Νέα έκδοση  ✅ Απομονωμένο  ✅ Εύκολο       │
└─────────────────────────────────────────────────┘
```

---

## Γιατί όχι την Μέθοδο 1 (apt);

Το Debian 13 (και γενικά οι νέες διανομές) έχουν στα repositories μια **παλιότερη έκδοση** του Ansible. Αυτή τη στιγμή το σύστημά σου έχει ήδη εγκατεστημένο το Ansible μέσω apt:

```bash
ansible --version
# ansible [core 2.19.4]
# executable location = /usr/bin/ansible  ← εγκατεστημένο από apt!
```

Αυτό δεν είναι πάντα πρόβλημα αν η έκδοση είναι αρκετά νέα. Στη δική σου περίπτωση το **2.19.4 είναι εξαιρετική έκδοση** — οπότε η apt έκανε καλή δουλειά αυτή τη φορά!

> 💡 **SysAdmin Deep Dive: Γιατί το `apt` δεν είναι ιδανικό για το Ansible;**
> Παρόλο που το `apt` είναι ο βασιλιάς της σταθερότητας στο Debian, για εργαλεία όπως το Ansible προκαλεί δύο βασικά προβλήματα στους διαχειριστές:
> 1. **Ταχύτητα Ενημερώσεων:** Το Ansible εξελίσσεται ραγδαία. Αν βγει ένα νέο module (π.χ. για AWS ή Docker), το `apt` του Debian μπορεί να κάνει μήνες ή και χρόνια να το ενσωματώσει στα repositories του. Με το `pip`, έχεις τη νέα έκδοση την ίδια μέρα.
> 2. **Αρχιτεκτονική (ARM / Banana Pi):** Σε πλακέτες όπως το Banana Pi/Raspberry Pi, συχνά τα OS repositories καθυστερούν να χτίσουν ενημερωμένα πακέτα για ARM αρχιτεκτονικές. Η Python (PyPI) αντίθετα, τρέχει απρόσκοπτα παντού.

---

## Γιατί έχει περιορισμούς το System-wide pip στο Debian 13;

Από το **Python 3.11+** και μετά, το Debian (και άλλες διανομές) εφαρμόζουν την πολιτική **PEP 668**. Αυτό σημαίνει ότι αν προσπαθήσεις να εγκαταστήσεις Python packages system-wide με pip, θα δεις:

```bash
pip install ansible
# ERROR: externally-managed-environment
# This environment is externally managed by apt.
# To install packages, use a virtual environment.
```

Ο λόγος είναι **ασφάλεια και σταθερότητα**: αν εγκαταστήσεις packages με pip system-wide, μπορεί να **συγκρουστούν** με packages που διαχειρίζεται το apt, σπάζοντας το σύστημα.

---

## Τι Γίνεται στις άλλες διανομές;

```
┌──────────────────┬────────────────────────────────────────┐
│ Διανομή          │ Συνιστώμενη Μέθοδος                    │
├──────────────────┼────────────────────────────────────────┤
│ Debian 13        │ pip μέσα σε venv (PEP 668)             │
│ Ubuntu 24.04+    │ pip μέσα σε venv (PEP 668)             │
│ Ubuntu 22.04     │ apt ή pip (χωρίς περιορισμό ακόμα)     │
│ Rocky/AlmaLinux  │ pip ή dnf (από EPEL repository)        │
│ CentOS Stream    │ pip ή dnf (από EPEL repository)        │
│ openSUSE         │ pip ή zypper (από community repo)      │
└──────────────────┴────────────────────────────────────────┘
```

### RedHat-based (Rocky, AlmaLinux):
```bash
# Μέσω EPEL repository
sudo dnf install epel-release -y
sudo dnf install ansible -y

# Ή μέσω pip με venv (ίδια λογική)
python3 -m venv ~/ansible/venv
source ~/ansible/venv/bin/activate
pip install ansible
```

### openSUSE:
```bash
# Μέσω zypper
sudo zypper install ansible

# Ή μέσω pip με venv
python3 -m venv ~/ansible/venv
source ~/ansible/venv/bin/activate
pip install ansible
```

> 💡 **Συμπέρασμα:** Το **pip μέσα σε venv** δουλεύει **παντού** ανεξαρτήτως διανομής. Γι' αυτό είναι η πιο portable λύση.

---

## Τι είναι το pipx και γιατί δεν το προτιμήσαμε;

Το **pipx** είναι ένα εργαλείο που εγκαθιστά Python εφαρμογές σε **αυτόματα απομονωμένα** virtual environments. Δηλαδή κάνει αυτόματα αυτό που εμείς κάνουμε χειροκίνητα με το venv.

```bash
# Με pipx:
pipx install ansible
# Αυτόματα φτιάχνει venv, εγκαθιστά, και προσθέτει στο PATH
# Τελείωσε! Δεν χρειάζεται activation.
```

### Γιατί **δεν** το διαλέξαμε:

```
┌─────────────────────────────────────────────────────────┐
│  pipx                                                   │
│  ✅ Απλό — μία εντολή και τελείωσε                      │
│  ✅ Αυτόματο isolation                                  │
│  ❌ Δεν βλέπεις τι γίνεται «κάτω από την κουβέρτα»      │
│  ❌ Λιγότερος έλεγχος του environment                   │
│  ❌ Δύσκολο να προσθέσεις extra Python libraries        │
│                                                         │
│  pip + venv (η επιλογή μας)                             │
│  ✅ Καταλαβαίνεις ΑΚΡΙΒΩΣ τι κάνεις                     │
│  ✅ Πλήρης έλεγχος του environment                      │
│  ✅ Εύκολη προσθήκη extra libraries (π.χ. boto3)        │
│  ✅ Ιδανικό για εκμάθηση                                │
│  ⚠️ Χρειάζεται manual activation                        │
└─────────────────────────────────────────────────────────┘
```

> 📝 **Σημείωση για τον Μαθητή:** Το pipx είναι εξαιρετικό για έμπειρους χρήστες που θέλουν ταχύτητα. Για εκμάθηση όμως, το **pip + venv** σε κάνει να καταλαβαίνεις τι συμβαίνει — και αυτό έχει αξία!

> 🧠 **Γιατί επιμένουμε στο χειροκίνητο venv και όχι στο pipx;**
> Το Ansible δεν είναι απλά ένα πρόγραμμα, είναι ένα **οικοσύστημα**. Σύντομα θα θέλεις το Ansible σου να διαχειρίζεται Windows (απαιτεί τη βιβλιοθήκη `pywinrm`), Cloud περιβάλλοντα (απαιτεί το `boto3`) κ.ά. 
> * Αν είσαι μέσα σε ένα δικό σου `venv`, απλά τρέχεις `pip install boto3` και το Ansible αποκτά αμέσως νέες "υπερδυνάμεις". 
> * Το `pipx` "κρύβει" αυτό το περιβάλλον, κάνοντας την προσθήκη έξτρα βιβλιοθηκών αχρείαστα περίπλοκη (`pipx inject...`).
> 
> Επιπλέον, το venv είναι η απόλυτη **Universal (Portable) Λύση**. Αν αύριο μεταφέρεις τα playbooks σου από το Debian σε ένα RedHat, Rocky Linux ή Ubuntu, η λογική "φτιάχνω έναν φάκελο, βάζω venv και τρέχω" παραμένει **ακριβώς η ίδια**. Δεν χρειάζεται να μαθαίνεις τις ιδιοτροπίες του package manager κάθε διανομής!

## Αφαίρεση του System Ansible (apt version)

Επειδή το σύστημά σου έχει ήδη εγκατεστημένο Ansible μέσω apt, **πρέπει να το αφαιρέσουμε πρώτα** για να αποφύγουμε συγχύσεις:

```bash
# Έλεγχος τι είναι εγκατεστημένο
dpkg -l | grep ansible

# Αφαίρεση ansible
sudo apt remove ansible -y

# Αφαίρεση και των dependencies που δεν χρειάζονται πια
sudo apt autoremove -y

# Επαλήθευση — δεν πρέπει να βρει τίποτα
ansible --version
# bash: ansible: command not found ✅
```

## Βήμα 3: Ενεργοποίηση Virtual Environment

```bash
# Ενεργοποίηση
source ~/ansible/venv/bin/activate

# Πρέπει να δεις:
# (venv) ansible@ansible-controller:~$
# ↑↑↑↑↑
# Το (venv) μπροστά = είσαι μέσα στο venv!
```

> ⚙️ **Πώς εκτελούμε τις εντολές της Ansible μέσα σε Virtual Environment;**
> 
> Εφόσον δεν εγκαταστήσαμε την Ansible σε όλο το σύστημα, το λειτουργικό (Debian) δεν ξέρει "πού να το βρει". Για να εκτελέσουμε εντολές (π.χ. `ansible-playbook`), υπάρχουν **τρεις προσεγγίσεις**:
> 
> **1. Η χειροκίνητη (Όπως κάναμε στο Βήμα 3)**
> Κάθε φορά που συνδέεσαι στο τερματικό, τρέχεις `source ~/ansible/venv/bin/activate`. Αυτό αλλάζει προσωρινά το περιβάλλον σου. Μόλις δεις το `(venv)` στην οθόνη, γράφεις απλά `ansible` και δουλεύει.
> 
> **2. Η αυτόματη (Η επιλογή μας για καθημερινή χρήση)**
> Αντί να γράφεις το παραπάνω κάθε φορά, θα πούμε στο λειτουργικό να το κάνει αυτόματα με το που κάνεις login. Αυτό ακριβώς θα σετάρουμε στο **Βήμα 6**, γλιτώνοντάς σου χρόνο.
> 
> **3. Το κόλπο των SysAdmins (Direct Execution - Χωρίς Activate!)**
> Δεν είναι *υποχρεωτικό* να ενεργοποιήσεις το venv! Μπορείς να καλέσεις το Ansible χρησιμοποιώντας το **απόλυτο μονοπάτι (absolute path)**.
> Παράδειγμα: `~/ansible/venv/bin/ansible --version`
> *Πότε είναι χρήσιμο αυτό;* Όταν θέλεις να τρέξεις την Ansible μέσω αυτοματισμού (π.χ. με `cron job` τα μεσάνυχτα ή μέσα από ένα CI/CD pipeline), όπου δεν υπάρχει "χρήστης" για να κάνει χειροκίνητο activate! Η Python θα καταλάβει από μόνη της ποιο περιβάλλον να χρησιμοποιήσει.

## Βήμα 6: Αυτόματη ενεργοποίηση venv

```bash
# Βγαίνουμε από το venv και είμαστε στο ansible@ansible-controller:$
deactivate

# Πρόσθεσε στο .bashrc του ansible user
cat >> ~/.bashrc << 'EOF'

# Αυτόματη ενεργοποίηση Ansible virtual environment
source ~/ansible/venv/bin/activate

# Μετάβαση στον ansible φάκελο
cd ~/ansible
EOF

# Εφάρμοσε τις αλλαγές
source ~/.bashrc

# Πρέπει να δεις:
# (venv) ansible@ansible-controller:~/ansible$
```

## Βήμα 7: Πρώτο Test Ansible & Privilege Escalation

Τώρα που εγκαταστήσαμε το Ansible, θα κάνουμε ένα test (ping) στο ίδιο μας το σύστημα. Εδώ όμως θα συναντήσουμε επίτηδες ένα από τα πιο κλασικά σφάλματα!

```bash
# Βεβαιώσου ότι είσαι στον ansible φάκελο
cd ~/ansible

# Δοκιμή ping στον localhost (το ίδιο το Banana Pi)
ansible localhost -m ansible.builtin.ping
```

**Αναμενόμενο Σφάλμα:**
```text
[ERROR]: Task failed: Premature end of stream waiting for become success.
>>> Standard Error
sudo: a password is required
localhost | FAILED! => {
    "changed": false,
    "msg": "Task failed: Premature end of stream waiting for become success.\n>>> Standard Error\nsudo: a password is required"
}
```

🧠 **Γιατί χτύπησε αυτό το λάθος; (SysAdmin Decoding)**
Το Ansible διάβασε το αρχείο ρυθμίσεων (`ansible.cfg`) που υπάρχει στον φάκελό μας, το οποίο του λέει από προεπιλογή να εκτελεί τις εντολές ως `root` (`become: yes`). Όταν όμως το Debian ζήτησε τον κωδικό του `sudo`, το Ansible (επειδή είναι αυτοματοποιημένο εργαλείο) "πάγωσε" περιμένοντας, και τελικά απέτυχε. 

Για να το λύσουμε αυτό, έχουμε **τρεις προσεγγίσεις**:

#### Λύση 1: Χειροκίνητη εισαγωγή κωδικού (Με την παράμετρο `-K`)
Μπορούμε να ζητήσουμε από το Ansible να μας εμφανίσει prompt για να γράψουμε τον κωδικό μας χρησιμοποιώντας το Κεφαλαίο `-K` (`--ask-become-pass`).
```bash
ansible localhost -m ansible.builtin.ping -K
# Θα σε ρωτήσει: BECOME password: (Βάζεις τον κωδικό σου)
# Αποτέλεσμα: SUCCESS! ✅
```

#### Λύση 2: Προσωρινή απενεργοποίηση του `become`
Εφόσον κάνουμε ένα απλό ping, δεν χρειαζόμαστε δικαιώματα διαχειριστή. Μπορούμε να παρακάμψουμε το `ansible.cfg` περνώντας μια extra μεταβλητή (`-e`) που λέει στο Ansible να παραμείνει ως απλός χρήστης.
```bash
ansible localhost -m ansible.builtin.ping -e "ansible_become=false"
# Αποτέλεσμα: SUCCESS! ✅
```

#### Λύση 3: Η μόνιμη λύση των SysAdmins (Passwordless Sudo) 🏆
Σε περιβάλλοντα αυτοματισμού, δεν μπορούμε να πληκτρολογούμε κωδικούς χειροκίνητα. Η βέλτιστη πρακτική είναι να ρυθμίσουμε το Linux ώστε ο χρήστης `ansible` να μπορεί να εκτελεί εντολές `sudo` **χωρίς** να του ζητείται κωδικός.

Για να το κάνουμε, δημιουργούμε έναν ειδικό κανόνα στον φάκελο `/etc/sudoers.d/`:
```bash
# Θα σου ζητηθεί ο κωδικός σου για τελευταία φορά
echo "ansible ALL=(ALL) NOPASSWD:ALL" | sudo tee /etc/sudoers.d/ansible
```
Αν τρέξεις τώρα την αρχική εντολή (`ansible localhost -m ansible.builtin.ping`), το ping θα περάσει **αυτόματα** χωρίς καμία ερώτηση!

---
💡 **Πώς συνδεόμαστε ως χρήστης Ansible από εδώ και πέρα;**
Σε μια επαγγελματική αρχιτεκτονική, μπαίνεις στον server σου με τον δικό σου προσωπικό χρήστη (π.χ. `admin` ή `pi`) και, όταν θέλεις να διαχειριστείς την υποδομή, "αλλάζεις" στον ειδικό χρήστη `ansible`.

Η εντολή για να το κάνεις (παίρνοντας μαζί και το περιβάλλον του - `venv`, κλπ) είναι:
```bash
sudo su - ansible
```
>*Η παύλα (`-`) είναι κρίσιμη: Λέει στο λειτουργικό "φόρτωσε το προφίλ και το `.bashrc` αυτού του χρήστη σαν να μόλις έκανε login", εξασφαλίζοντας ότι θα ενεργοποιηθεί αυτόματα το venv μας (Βήμα 6)!*
