# 22.1 Γιατί Testing στην Ansible ✅

## Το πρόβλημα

Χωρίς testing, η Ansible code:

```
Κίνδυνοι χωρίς testing:
│
├── ❌ Idempotency bugs
│   └── Το playbook αλλάζει κάτι σε κάθε run
│       (το σύστημα δεν σταθεροποιείται)
│
├── ❌ Syntax errors
│   └── Ανακαλύπτονται σε production...
│
├── ❌ Logic errors
│   └── "Δούλευε στο laptop μου"
│
├── ❌ Compatibility issues
│   └── Δουλεύει σε Ubuntu, σπάει σε RHEL
│
└── ❌ Regression
    └── Νέα αλλαγή σπάει παλιά λειτουργία
```

---

## Τα επίπεδα testing

```
Testing Pyramid για Ansible:
│
├── Static Analysis (ansible-lint)
│   ├── Σύνταξη & style
│   ├── Best practices
│   └── ⚡ Πολύ γρήγορο (δευτερόλεπτα)
│
├── Unit Testing (Molecule)
│   ├── Role testing σε container
│   ├── Idempotency check
│   └── ⏱️ Λεπτά
│
└── Integration Testing
    ├── Full playbook σε VM
    └── ⏰ Ώρες (CI/CD pipeline)
```

---

## Idempotency — Το κρίσιμο property

```
Idempotent playbook:
  1η εκτέλεση: changed=5, failed=0 ✅
  2η εκτέλεση: changed=0, failed=0 ✅ (ίδιο αποτέλεσμα!)
  3η εκτέλεση: changed=0, failed=0 ✅

Non-idempotent:
  1η εκτέλεση: changed=5, failed=0 ✅
  2η εκτέλεση: changed=5, failed=0 ❌ (αλλάζει πάλι!)
```

---

## Σύνοψη 22.1

```
Γιατί Testing:
│
├── Idempotency → αποφυγή side effects
├── Syntax/lint → πριν την εκτέλεση
├── Role testing → πριν το production
└── Regression  → "δεν σπάω τίποτα"

Tools:
├── ansible-lint → static analysis
└── Molecule     → role testing framework
```
