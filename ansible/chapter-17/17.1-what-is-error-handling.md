# 17.1 Τι είναι το Error Handling 🛡️

## Ο ορισμός

Το **Error Handling** είναι ο μηχανισμός με τον οποίο λέμε στην Ansible **τι να κάνει όταν κάτι πάει στραβά** κατά την εκτέλεση ενός playbook.

> 📝 **Αναλογία:** Σκέψου την Ansible σαν ένα **χειρουργείο**:
> ```
> Χωρίς Error Handling:
> Αν κάτι πάει λάθος → ΟΛΑ σταματούν αμέσως ❌
>
> Με Error Handling:
> Αν κάτι πάει λάθος → Έχεις plan B, plan C,
>                        cleanup, αναφορά, rollback ✅
> ```

---

## Η default συμπεριφορά

Από προεπιλογή, η Ansible:

```
1. Ένα task αποτυγχάνει (exit code != 0)
        │
        ▼
2. Το host μαρκάρεται ως "FAILED"
        │
        ▼
3. ΔΕΝ εκτελούνται άλλα tasks σε αυτό το host
        │
        ▼
4. ΔΕΝ εκτελούνται οι handlers
        │
        ▼
5. Το playbook τελειώνει με σφάλμα
```

```bash
# Παράδειγμα — τι βλέπεις όταν αποτύχει task:
TASK [Εγκατάσταση κάποιου package] *****
fatal: [nextcloud]: FAILED! => {
    "changed": false,
    "msg": "No package matching 'nonexistent-pkg' is available"
}

PLAY RECAP ***************************
nextcloud  : ok=2  changed=0  unreachable=0  failed=1
```

## Γιατί χρειαζόμαστε Error Handling

### Σενάριο 1: Εντολές που «αποτυγχάνουν» φυσιολογικά

```yaml
tasks:
  # Αυτό "αποτυγχάνει" αν το process δεν τρέχει
  # αλλά εμείς ΔΕΝ θέλουμε να σταματήσει το playbook
  - name: Σταμάτα το service αν τρέχει
    ansible.builtin.command:
      cmd: systemctl stop myapp
    # Χωρίς handling → αποτυχία αν δεν τρέχει ❌
```

### Σενάριο 2: Διαφορετικό κριτήριο αποτυχίας

```yaml
tasks:
  - name: Έλεγχος disk usage
    ansible.builtin.shell:
      cmd: "df / | tail -1 | awk '{print $5}' | tr -d '%'"
    # Αυτό ΠΑΝΤΑ επιτυγχάνει (exit 0)
    # αλλά εμείς θέλουμε να αποτύχει αν disk > 90% ❌
```

### Σενάριο 3: Cleanup μετά από σφάλμα

```yaml
tasks:
  - name: Deploy νέα έκδοση
    # Αν αποτύχει → θέλουμε rollback + cleanup ❌
    # Χωρίς block/rescue: τίποτα δεν γίνεται αυτόματα
```

## Τα εργαλεία Error Handling

```
Error Handling Toolkit
│
├── ignore_errors: true
│   └── «Αγνόησε το σφάλμα και συνέχισε»
│
├── failed_when: <condition>
│   └── «Θεώρησε αποτυχία ΜΟΝΟ αν ισχύει αυτό»
│
├── changed_when: <condition>
│   └── «Θεώρησε αλλαγή ΜΟΝΟ αν ισχύει αυτό»
│
├── block / rescue / always
│   ├── block:   «Δοκίμασε αυτά τα tasks»
│   ├── rescue:  «Αν αποτύχει → κάνε αυτά»
│   └── always:  «Κάνε αυτά ΠΑΝΤΑ (cleanup)»
│
├── debug module
│   └── «Εκτύπωσε μεταβλητές/μηνύματα»
│
└── assert module
    └── «Επαλήθευσε ότι κάτι ισχύει»
```

---

## Πότε χρειάζεσαι Error Handling

```
✅ Όταν χρησιμοποιείς command/shell modules
   (δεν είναι idempotent — δεν ξέρουν τι άλλαξε)

✅ Όταν κάνεις deployment σε production
   (θέλεις rollback αν κάτι πάει λάθος)

✅ Όταν ελέγχεις κατάσταση service/process
   (το "δεν τρέχει" δεν είναι πάντα σφάλμα)

✅ Όταν γράφεις roles που θα χρησιμοποιούν άλλοι
   (πρέπει να είναι robust)

✅ Όταν κάνεις cleanup (directories, temp files)
   (πρέπει να γίνει ΠΑΝΤΑ, ακόμα κι αν αποτύχει)

❌ Δεν χρειάζεσαι για builtin modules
   (apt, dnf, copy, template κ.λπ.)
   → Αυτά επιστρέφουν σωστά exit codes
```

## Η ροή Error Handling

```
Task εκτελείται
       │
       ▼
   Επιτυχία; ──── ΝΑΙ ────► Επόμενο task ✅
       │
       ΟΧΙ
       │
       ▼
  ignore_errors: true; ──── ΝΑΙ ────► Επόμενο task ✅
       │                               (με warning)
       ΟΧΙ
       │
       ▼
  Είμαστε σε block; ──── ΝΑΙ ────► rescue: section 🛟
       │
       ΟΧΙ
       │
       ▼
  Host: FAILED ❌
  Σταματά η εκτέλεση για αυτό το host
```

## Σύνοψη 17.1

```
Error Handling — Τι είναι
├── Default: αποτυχία task = σταμάτα όλα
│
├── Γιατί χρειάζεται:
│   ├── Commands που "αποτυγχάνουν" φυσιολογικά
│   ├── Custom κριτήρια αποτυχίας
│   └── Cleanup/rollback μετά από σφάλμα
│
└── Εργαλεία:
    ├── ignore_errors   → αγνόησε σφάλμα
    ├── failed_when     → custom αποτυχία
    ├── changed_when    → custom αλλαγή
    ├── block/rescue    → try-catch
    ├── debug module    → εκτύπωση info
    └── assert module   → επαλήθευση
```
